# PRP: Executive & Operational Dashboard

## METADATA

- **Module**: Executive & Operational Dashboard (`docs/ARCHITECTURE.md` §9, item 8 — the final module in the build-out order, "depends on all of the above existing")
- **Depends on**: Ward/Bed (occupancy), Queue (wait-times — see design decision #2 for why this is a documented gap, not a full dependency), Billing (revenue), Appointments (no-shows), Pharmacy (stock-alerts)
- **Replaces**: `backend/app/routers/dashboard.py`'s existing STUB (5 TODO endpoints, read below — this PRP implements exactly those 5, no more)
- **Shape**: unlike every prior module, this one adds **no new tables and no new ORM models**. It is a pure read-aggregation layer over data that already exists (`beds`, `queue_tokens`, `invoices`, `appointments`, `inventory_items`/`inventory_batches`). There is no engine with locking/concurrency correctness to design — the hard part here is writing correct, efficient aggregate SQL and being honest about what the underlying data can and cannot support.

## MODULE OVERVIEW — key design decisions

1. **Access is `system_admin` only, for all five endpoints.** This codebase's `UserRole` enum (`backend/app/models/user.py`) has no `executive`/`branch_admin`/`hospital_admin` role — the only role with cross-branch, non-clinical, operational-oversight scope is `system_admin`. Rather than inventing a new role not asked for anywhere in the architecture doc, this PRP scopes the entire module to `system_admin`. Every endpoint takes an **optional** `branch_id` query param: omitted means "aggregate across every branch" (system_admin has no branch of their own, so there is no "my branch" default the way there is for `pharmacist`/`billing_admin` elsewhere), supplied means "scope to this one branch." This is a deliberate divergence from every prior module's `_resolve_branch_filter` (which exists specifically to let a non-admin role's own branch flow through) — there is no non-admin caller here, so `_resolve_branch_filter` itself is not reused; a query-param-only branch filter is all that's needed. `authorize()`'s tenant guard still isn't bypassed accidentally: since every resource here is a plain aggregate (no single ORM row with a `branch_id` attribute to check), and the only role that can reach any of these five service functions is `system_admin` (gated by `require_role("system_admin")` at the router), there is nothing left for a resource-level `authorize()` call to add — see design decision #5 for why no `authorize()`/`@policy(...)` registration was added for this module.

2. **`GET /dashboard/wait-times` is a real, working aggregation over `queue_tokens` — but that table currently has (and will continue to have) zero rows in this deployment**, because `routers/queue.py` (the Real-Time Queue module) is still its own STUB (check-in/status-transition endpoints were never built — it isn't in `docs/ARCHITECTURE.md` §9's 8-item build-out list at all, only mentioned under §1 "Scope of this delivery" as WebSocket broadcast infrastructure that already exists). This PRP does **not** build the queue module — that would be scope creep into a different, unbuilt module. The wait-times query is written correctly against `QueueToken.checked_in_at`/`called_at` and will start returning real numbers the moment a future PRP builds `routers/queue.py`'s check-in endpoint and starts writing rows — exactly the same "generic machinery, currently-empty data source" shape `notification_engine.py`'s `_TOPIC_HANDLERS` used for topics that hadn't started publishing yet. Document this plainly in the endpoint's docstring; do not fake sample data or skip the endpoint.

3. **`GET /dashboard/no-shows` reports the actual no-show rate only — it does NOT compare against `no_show_risk_score` predictions**, despite the stub's TODO comment suggesting exactly that comparison ("trend vs no_show_risk_score predictions to evaluate the heuristic/model"). A repo-wide grep confirms `Appointment.no_show_risk_score` (`models/appointment.py`) is written nowhere in this codebase — no scoring service/heuristic/model exists anywhere to populate it. Comparing actual outcomes against predictions that are never generated is not possible; building a scoring engine is a substantial new module of its own, entirely out of scope for a dashboard PRP. Report the column's `NULL`-only reality plainly in the response schema's docstring rather than silently omitting any mention of it.

4. **`GET /dashboard/revenue` buckets by `Invoice.created_at`, not by "date paid."** `models/billing.py`'s `Invoice` has no `paid_at`/`updated_at` column — only `created_at` (set once, at invoice-open time) and a `status` column that changes in place. This means "collected on day X" cannot be computed exactly (a same-day invoice paid three weeks later is indistinguishable from one paid the same day, in this schema). The endpoint reports, per day bucketed by `created_at`: `invoice_count`, `gross_billed` (`SUM(total_amount)` for every non-`void` invoice opened that day, regardless of current status), and `collected` (`SUM(total_amount)` for invoices opened that day whose *current* status happens to be `paid` — an approximation, not a true "cash received on this date" figure). This limitation is documented in the response schema and the service function's docstring, not silently glossed over — same "state not tracked, don't pretend otherwise" discipline Billing's own PRP used for claim-state-not-linked-to-invoice-state.

5. **No new `@policy(...)` registrations in `core/security.py`.** Every prior module registered ABAC policies because at least one non-`system_admin` role needed access to a resource with a real `branch_id` to check the tenant guard against. Here, `require_role("system_admin")` at the router is the entire access control surface — `system_admin` already bypasses `authorize()`'s tenant guard unconditionally (`_admin_bypass`), and no other role is ever routed to these five functions, so a resource-scoped `authorize()` call would be checking a condition that can never fail. Calling `authorize()` anyway "for consistency" would be dead code — this PRP deliberately omits it, matching the "don't add validation for scenarios that can't happen" project convention. If a future PRP ever adds a non-`system_admin` role to any dashboard endpoint, that is exactly the point at which real `@policy(...)` registrations and `authorize()` calls need to be added — not before.

6. **`stock-alerts` reuses `pharmacy_service.get_low_stock`/`get_expiring` directly rather than reimplementing the aggregation.** Both already exist (`backend/app/services/pharmacy_service.py`, lines ~352 and ~411), already accept an optional `branch_id_param` (`None` = all branches) and a `current_user`, and already return `LowStockItemResponse`/`ExpiringBatchResponse` schemas. The dashboard service function is a thin call-through: `pharmacy_service.get_low_stock(db, current_user, branch_id)` / `pharmacy_service.get_expiring(db, current_user, branch_id, within_days=30)`. Do not copy the SQL — call the existing functions. (Note their internal `_resolve_branch_filter`/`authorize` calls are no-ops for a `system_admin` caller — `_resolve_branch_filter` just returns `branch_id_param` unchanged for that role — so this call-through is safe and adds no redundant restriction.)

7. **No materialized view / read replica**, despite the existing stub's own TODO comment suggesting one ("plan for a materialized view... rather than hitting primary OLTP tables directly"). At this codebase's scale (a scaffold, no real traffic), the five aggregate queries below are simple `GROUP BY`/`SUM`/`COUNT` queries against small tables — introducing a materialized view (with its own refresh-staleness tradeoffs to design and document) is premature optimization for a problem that doesn't exist yet. Direct queries against the primary tables are correct and sufficient; a caching/materialized-view layer is a real, separate, future PRP if/when real traffic ever demands it.

## SERVICE DESIGN — `backend/app/services/dashboard_service.py`

Five public functions, one per endpoint, each taking `(db: Session, current_user: User, branch_id: uuid.UUID | None)` (plus a `days`/`within_days` window param where relevant). None require locking (pure reads, no state to protect). `current_user` is accepted for signature consistency with every other service module in this codebase even though (per design decision #5) it is never actually used for an authorize() call — router-level `require_role("system_admin")` is the sole gate. Do not add a dead `# type: ignore` or drop the parameter; keep it for consistency and because `require_role`'s dependency already guarantees it's always `system_admin` by the time this function runs.

```python
def get_occupancy(db: Session, current_user: User, branch_id: uuid.UUID | None) -> list[WardOccupancyResponse]: ...
def get_wait_times(db: Session, current_user: User, branch_id: uuid.UUID | None, days: int) -> list[DepartmentWaitTimeResponse]: ...
def get_revenue(db: Session, current_user: User, branch_id: uuid.UUID | None, days: int) -> list[DailyRevenueResponse]: ...
def get_no_show_rate(db: Session, current_user: User, branch_id: uuid.UUID | None, days: int) -> NoShowRateResponse: ...
def get_stock_alerts(db: Session, current_user: User, branch_id: uuid.UUID | None) -> StockAlertsResponse: ...
```

- `get_occupancy`: one query joining `Ward` -> `Bed`, grouped by `(ward.branch_id, ward.id, ward.name, ward.ward_type)`, computing `total_beds = COUNT(bed.id)` and `occupied_beds = COUNT(bed.id) FILTER (WHERE bed.status = 'occupied')` (SQLAlchemy: `func.count(Bed.id).filter(Bed.status == BedStatus.occupied)` or an equivalent `case()` sum — either is fine, whichever compiles cleanly against the existing Postgres version already in use). `occupancy_pct = occupied_beds / total_beds` (as a `float`, guard the zero-bed-ward division). Filter by `Ward.branch_id == branch_id` only when `branch_id is not None`.
- `get_wait_times`: query `QueueToken` where `checked_in_at >= now() - days` AND `called_at IS NOT NULL` (only tokens that were actually called count toward a wait time — a still-waiting or skipped token has no completed wait to measure), grouped by `(branch_id, department_id)`, `avg_wait_minutes = AVG(EXTRACT(EPOCH FROM (called_at - checked_in_at)) / 60)`, plus `sample_size = COUNT(*)`. Join `Specialty` for `department_name` (same N+1-avoidance discipline `pharmacy_service.get_low_stock` uses — one joined query, not a per-row lookup). Per design decision #2, this will return `[]` in this deployment today — that's correct, expected behavior, not a bug to work around.
- `get_revenue`: query `Invoice` where `created_at >= now() - days` AND `status != 'void'`, grouped by `(branch_id, DATE(created_at))`. Per-group: `invoice_count = COUNT(*)`, `gross_billed = SUM(total_amount)`, `collected = SUM(total_amount) FILTER (WHERE status = 'paid')`, `outstanding = gross_billed - collected`. See design decision #4 for why `collected` is an approximation.
- `get_no_show_rate`: query `Appointment` where `time_range`'s lower bound falls in `[now() - days, now()]`. CORRECTION: a grep of `services/scheduling_engine.py` confirms it does NOT have an existing "extract the lower bound of a tstzrange for a plain date-window filter" helper — it only uses range *overlap*/*strictly-after* operators (`.op("&&")`, `.op(">>")`) for booking-conflict checks, a different concern. Use Postgres's own `func.lower(Appointment.time_range)` (SQLAlchemy `from sqlalchemy import func; func.lower(Appointment.time_range) >= window_start`) directly here — this is the first place in the codebase filtering appointments by a plain reporting time-window rather than a conflict check, so there is nothing existing to reuse; don't invent a false precedent, just write the correct, standard range-lower-bound extraction. Excluding `status IN ('cancelled', 'preempted')` — neither was ever a no-show *or* a completed visit; `preempted` is grouped with `cancelled` in the same "no longer an active booking" category `models/appointment.py`'s own EXCLUDE constraint and `emergency_engine.py` already use, and a preempted appointment was bumped by the system for a higher-priority emergency, not a patient no-show, so counting it would understate the true rate. Neither is numerator or denominator; only `no_show` counts as numerator, and every other status counts toward the denominator. Return one aggregate `NoShowRateResponse` when `branch_id` is supplied, or a `list[...]` grouped by branch when it's omitted — **pick ONE of these two shapes and be consistent with `get_occupancy`/`get_revenue`'s existing list-of-groups shape** (recommend: always return `list[NoShowRateResponse]` grouped by `branch_id`, one row per branch, for symmetry with the other four endpoints — simpler for the frontend to render uniformly). Include a `no_show_risk_score_note: str` field or module-docstring-only note (your call at Phase 2) surfacing design decision #3's honesty about the unused column — a hardcoded fixed string is fine, this is documentation, not a computed field.
- `get_stock_alerts`: per design decision #6, call `pharmacy_service.get_low_stock(db, current_user, branch_id)` and `pharmacy_service.get_expiring(db, current_user, branch_id, within_days=30)` directly, bundle both lists into one `StockAlertsResponse { low_stock: list[LowStockItemResponse], expiring_soon: list[ExpiringBatchResponse] }` (reuse those exact existing schemas from `schemas/pharmacy.py` — import them, don't redefine).

## PHASE EXECUTION PLAN

- **Phase 1** (single BACKEND-AGENT): `services/dashboard_service.py` only. Validation Gate 1: run all five functions directly against the live dev Postgres container (`docker compose up -d postgres redis`, already-seeded data from prior modules' own test runs, or freshly inserted fixture rows if the DB is empty) and eyeball that the aggregate numbers are sane (occupancy between 0-100%, revenue sums match a manual `SELECT SUM(total_amount) FROM invoices` sanity check, etc.) — this replaces the "live DB round-trip" gate every prior module's Phase 1 used, adapted for a read-only module (no insert/update round-trip to verify, just correct aggregation).
- **Phase 2** (BACKEND-AGENT + FRONTEND-AGENT in parallel): schemas + router (backend), types + service + page + route (frontend). Identical API contract given to both, per this session's established parallel-agent pattern.
- **Validation Gate 2**: `py_compile`/`import app.main`, `tsc --noEmit`, no `docker-compose.yml`/`schema.sql` changes to validate this time (none are made).
- **Phase 3** (TEST-AGENT + REVIEW-AGENT in parallel): TEST-AGENT writes `backend/tests/test_dashboard_service.py` + `backend/tests/test_dashboard_router.py` against the real DB (seed wards/beds/invoices/appointments/inventory fixtures, assert correct aggregation, assert `system_admin`-only role gating, assert branch_id filtering). REVIEW-AGENT checks: correctness of the aggregate SQL (off-by-one on window boundaries, correct handling of `branch_id IS NULL` meaning "all branches" vs accidentally filtering nothing), whether `get_no_show_rate`'s time-range lower-bound extraction matches `scheduling_engine.py`'s own established pattern exactly, whether `get_stock_alerts` really does call-through to `pharmacy_service` rather than duplicating its logic, and whether the honest documentation of design decisions #2/#3/#4 (empty wait-times table, no risk-score comparison, approximate "collected" figure) survived into the actual code's docstrings/comments rather than being silently dropped during implementation.

1. Gate 1 (Phase 1): live DB aggregate sanity check, no round-trip insert needed (read-only module).
